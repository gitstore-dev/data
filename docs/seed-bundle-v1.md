# GitStore seed bundle v1

This is the normative contract for `gitstore.seed/v1`. It distributes English
Shopify CategoryTaxonomy data independently of GitStore services. It neither
executes code nor installs resources. Dataset version (currently `0.1.0`),
upstream taxonomy version (`2026-11`), and package format (`gitstore.seed/v1`)
are separate identities. Unknown package formats, resource APIs and media types
must be rejected before resource writes. These vendor media types are defined
here; no IANA registration is claimed.

## OCI representation

Use the [OCI 1.1 artifact conventions](https://github.com/opencontainers/image-spec/blob/v1.1.1/manifest.md#guidelines-for-artifact-usage)
and [OCI image layout](https://github.com/opencontainers/image-spec/blob/v1.1.1/image-layout.md).
Each selection has its own manifest and is independently addressable by its
manifest SHA-256 digest. There is no platform, OS, architecture, entrypoint,
container root filesystem configuration or runnable image.

| Field | Value |
| --- | --- |
| Manifest `schemaVersion` | `2` |
| Manifest `mediaType` | `application/vnd.oci.image.manifest.v1+json` |
| Manifest `artifactType` | `application/vnd.gitstore.seed.v1` |
| Config media type | `application/vnd.oci.empty.v1+json` |
| Config content | Exactly two bytes: `{}` |
| Single layer media type | `application/vnd.gitstore.seed.v1.tar+gzip` |
| Layer title annotation | `org.opencontainers.image.title: seed.tar.gz` |

The manifest records source repository, source commit, dataset version, MIT
license and selection annotations. Config, manifest and layer descriptors use
SHA-256 and exact byte sizes. The generated layout contains:

```text
oci-layout                       # imageLayoutVersion: 1.0.0
index.json                       # one descriptor; local ref <version>-<selection>
blobs/sha256/<config-sha256>      # {}
blobs/sha256/<manifest-sha256>    # exact manifest.json bytes
blobs/sha256/<archive-sha256>     # exact seed.tar.gz bytes
manifest.json                    # readable copy for offline identity inspection
seed.tar.gz                      # standalone offline payload
checksums.json                   # archive and OCI-manifest descriptors, separately
```

Publication must copy these manifest/blob bytes unchanged, rather than invoke a
new registry push recipe that rewrites annotations or config. Registry upload,
release assets and publisher attestations use the [release workflow](releases.md). OCI tooling is
optional for maintainers; no ORAS, Git or Python executable is in the payload.

## Payload and bundle manifest

The archive contains regular files only. `bundle.json` is first, followed by
all other paths in ASCII order. Allowed paths are exactly:

- `bundle.json`: package manifest, described below.
- `dataset.json`: the selection/export metadata from data #1, unchanged.
- `LICENSE` and `LICENSE-SHOPIFY`: complete retained license notices.
- `categories/<two-letter-vertical>/<Shopify ID>.md`: selected canonical bytes.

There are no directory entries, links, devices, FIFO entries, PAX/GNU extensions,
sparse files, whiteouts, absolute paths, `.`/`..` components, backslashes, drive
prefixes, executable permissions or unexpected files. Source/editorial JSONL,
Git history, tools, scripts, virtual environments, credentials, File resources,
media references, media binaries and LFS objects are excluded.

Except for the standardized two-byte empty OCI config, JSON generated by this
contract is UTF-8 with unescaped Unicode, sorted object keys, two-space
indentation and a final newline (Python `json.dumps`,
`ensure_ascii=False, sort_keys=True, indent=2`, plus `\n`). Duplicate JSON keys
and non-finite numbers are invalid. Digests are `sha256:` followed by 64 lowercase
hexadecimal characters; inventory `sha256` fields contain the hexadecimal part.

`bundle.json` has the following required fields. The reference verifier rejects
additional package-manifest fields in v1; an extension needs a contract change.

| Field | Meaning |
| --- | --- |
| `package_format` | Exactly `gitstore.seed/v1` |
| `dataset` | Name `shopify-categories`, dataset `version`, `selection`, metadata path `dataset.json` |
| `source` | Repository URL, full committed-input Git SHA-1, and complete pinned Shopify taxonomy source lock |
| `requirements` | Resource APIs and required target capabilities |
| `resources` | Resource count, root count, manifest bytes, ordering and resource-inventory checksum from `dataset.json` |
| `provenance` | Selection-lock checksum and pinned parser/schema compatibility evidence |
| `licenses` | Ordered paths `LICENSE`, `LICENSE-SHOPIFY` |
| `files` | Every other file, ASCII path order; exact `path`, `bytes`, `sha256` |
| `file_count` | All regular files, **including** `bundle.json` |
| `expanded_bytes` | Sum of all regular-file lengths, **including** `bundle.json`; excludes tar headers/padding |

`bundle.json` has no self-checksum: the archive/OCI descriptors bind it. Its
expanded-size field is calculated to a fixed point after serialization. The
committed selection lock binds source/editorial inputs and inventories; the
builder refuses dirty/untracked canonical, selection or builder inputs so its
source commit identifies the actual inputs. The provenance fields are claims
bound to content, not independent proof of the producer's identity.

The complete per-resource inventory in `dataset.json` records IDs, stable names,
exact titles, parent names, paths, sizes and checksums. It is ordered by ancestor
depth, then ASCII category ID; all parents precede children. Tar order is a
storage order, **not** admission order: importers must use this inventory. Full
parent closure, unique identities, root/vertical counts, local navigation and
licenses must validate. The v1 resource API is
`catalog.gitstore.dev/v1beta1`, kind `CategoryTaxonomy`. Author-writable metadata
contains only `name` and provenance `annotations`; spec contains `title` and,
for children, a namespace-free `parentRef`. Namespace, system-managed fields
and media slots are absent. License notices are nonempty printable UTF-8 MIT
notices, not arbitrary binary files. Consumer validation never rewrites category bytes.

## Reproducibility profile and limits

The reference writer uses USTAR: each file has mode `0644`, numeric UID/GID and
mtime zero, empty user/group/link names, no prefix or extension metadata, and
canonical header checksums. File padding and the two-block end marker are zero;
the complete tar is zero-padded to the next 10,240-byte record boundary. The
verifier requires these exact headers/padding, not permissive tar extraction.

Gzip is a single member with no filename/comment/extra fields and header
`1f8b08000000000002ff`: mtime zero, compression level 9, OS byte 255. DEFLATE uses
the reference Python/zlib level-9 implementation. CRC32 and ISIZE must validate;
trailing data and concatenated members are rejected. Do not infer a unique gzip
encoding from uncompressed content alone. The checked-in digest vectors pin actual
codec output; maintainers must check fixture and repeated-build reproducibility
when changing Python/zlib, and publication should pin its builder environment.
Archives are architecture-independent data, not platform-specific executables.

Consumers may choose lower limits, but must enforce finite limits before
allocating or extracting. The v1 reference upper bounds are:

| Limit | Maximum |
| --- | ---: |
| Compressed archive | 128 MiB |
| Total uncompressed tar stream, including headers/padding | 640 MiB |
| Declared and actual regular files | 70,000 |
| Total regular-file bytes, including metadata | 512 MiB |
| Each metadata JSON file | 64 MiB |
| Each category Markdown file | 1 MiB |
| Each license notice | 64 KiB |

Verify the compressed digest and size before decompression. Use bounded
streaming decompression; reject declared/actual limits, duplicate paths, invalid
headers, padding, footer and CRC. Parse `bundle.json`, reject unsupported formats
and requirements, and verify every declared file and exact inventory. Validate
resource semantics, parent closure and navigation; reject undeclared files.
Never pass an untrusted archive to `extractall` or follow archive links. The
reference verifier stages a bounded tar in a temporary file and does not retain
all resource bodies in memory. Optional extraction happens only after complete
verification, into a fresh staging directory atomically renamed to an absent
destination. The entire OCI envelope is checked before extraction in package mode.

## Compatibility and trust

`requirements.capabilities` includes `repository-scoped-namespace-inference`;
`requirements.resource_apis` includes the category API above. These are contract
identifiers, not a claim that a particular deployed discovery endpoint exists.
An importer must obtain authoritative target support, compare **all** required
capabilities and APIs, and fail before any resource write if support is absent
or unresolved. The verifier's optional target flags check explicitly supplied
sets; they do not contact a server. Omitted flags mean content verification only.
A merged namespace-inference change or pinned parser revision does not prove
that the target API deployment is compatible. No namespace is inserted in files.

The OCI manifest digest hashes the exact manifest JSON. The archive digest
hashes `seed.tar.gz`; they are different identities. An offline archive can be
verified against its archive digest without a registry or the authoring source.
Offline layout verification additionally follows the index, manifest, empty
config and layer digest chain. Supply an expected digest obtained through an
approved release channel; a self-consistent package alone does not authenticate
its publisher. Hashes do not provide signatures, producer authorization, or
proof that upstream labels are official. Signature/provenance trust policy is a
separate publication/consumer concern. No verified package implies successful
admission, controller readiness, replay safety or production capacity.

## Consumer fixtures

[`tests/fixtures/seed-v1`](../tests/fixtures/seed-v1) contains only a text fixture
definition and expected digest vectors. The recipe generates a complete 14 KiB
offline layout for the three Gift Cards categories, version `0.0.0-fixture`,
selection `fixture-gift-cards`. It is not a published starter/full dataset.
Its canonical data source is commit `04df0a756d4ec7d2ad359ff9cc526ef26d3c018e`;
the fixture recipe defines the reduced selection. `vectors.json` pins archive,
OCI manifest and empty-config digests, sizes, requirements and expanded counts.
Generate it locally for CLI reader tests; committed canonical inputs suffice,
with no network or generation service. The generated layout is standalone input.

The tests generate fixtures in temporary directories, compare their bytes and
the committed digest vectors, verify both identity paths,
compare extracted resources with canonical bytes, and exercise tampering,
unsafe entries, limits, missing requirements, invalid resources, parent closure,
navigation and output preservation. Regenerate intentionally into a fresh path:

```sh
.venv/bin/python tests/bundle_fixture.py --output /tmp/seed-v1-fixture
```

Do not commit generated archives or OCI blobs. Review definition/vector changes
explicitly; tests never refresh committed expected digests. CI generates only
this tiny fixture alongside existing data verification. Production bundles are
built for release/publication, not stored in Git. CI does not build full bundles,
install OCI clients, run GitStore or publish anything. Git LFS remains reserved
for future `media/**` source assets; generated packages do not belong in LFS.
